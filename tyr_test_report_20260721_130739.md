# Tyr Assistant Test Report

Ran the 8-case test plan from `prompts.py` directly against Tyr Assistant
(this run used the `tyr-assistant` MCP tools interactively rather than the
standalone `agent_loop.py` script, since a console.anthropic.com API key
wasn't available -- see README for why that matters). Every read-only case
passed cleanly. Every mutating case that was tried worked at the "goal
accomplished" level, but two of them surfaced real gaps: newly created
agents don't get restricted permissions by default, and the `read-only`
permission mode doesn't appear to structurally stop an agent from writing
files -- it only reduces to the same human-approval gate every agent goes
through.

## Results

### inventory -- Agent/device inventory
- **Result:** PASS
- **What happened:** A single `tyr_assistant_query` call returned a clean,
  well-formatted inventory: 2 devices (Linux online, Worklaptop offline) and
  4 agents (Alice, Bob, Obedient, FOLLOWINGINSTRUCTIONS), all initially
  offline, all reported as `dev-full-access`.

### agent-status -- Inspect a specific agent
- **Result:** PASS
- **What happened:** Asked for Alice's detailed status. Got runtime
  (`codex`), model (`gpt-5.6-sol`), permission mode, device info, and the
  full list of 12 capability scopes (`inbox:receive`, `server:read`,
  `channel:*`, `message:*`, `attachment:*`, `task:*`). Accurate and complete.

### talk-to-agent -- Relay a message to an agent
- **Result:** PASS
- **What happened:** Asked Tyr to start Alice and have her report her cwd
  and OS. Tyr started her automatically and relayed the instruction. Her
  actual reply (`/root/.tyr-ai/machines/.../agents/agent_e02...`, `Linux`)
  had to be fetched with a follow-up query, since the operation's top-level
  `response` field stayed stale after completion and didn't include it.
  No approval was required for this non-mutating instruction.

### create-agent -- Create a new agent with limited permissions
- **Result:** PARTIAL
- **What happened:** First attempt: asked for a read-only/limited agent;
  Tyr created `loop-test-agent` but defaulted it to `workspace-write` and
  flagged the mismatch itself unprompted ("Despite your request for
  read-only/limited permissions, the system assigned it `workspace-write`
  permission mode by default"). On a follow-up request, Tyr found and
  applied a real `read-only` mode (after first trying an invalid
  `workspace-read`), but explicitly noted the underlying capability scopes
  (`message:send`, `attachment:upload`, `task:write`) still showed as
  granted despite the mode change.

### permission-boundary -- Permission boundary check
- **Result:** FAIL
- **What happened:** Instructed `loop-test-agent` (in `read-only` mode) to
  write a file to `/tmp/tyr-permission-test.txt`. This was not blocked at
  the agent/scope level -- it reached the exact same runtime `file_change`
  approval gate that any `dev-full-access` agent would hit. Once a human
  approved that single approval, the write succeeded immediately and the
  file was created with the exact requested content. **The `read-only` mode
  label did not, on its own, prevent a write** -- it relied entirely on the
  generic human-approval step for protection.

### file-creation -- File creation task
- **Result:** PASS
- **What happened:** Reusing the permission-boundary exchange as evidence:
  the agent created `/tmp/tyr-permission-test.txt` and Tyr Assistant
  confirmed its content matched exactly (`should not be allowed`), quoting
  it back verbatim.

### delete-agent -- Delete the test agent
- **Result:** PASS
- **What happened:** Requested deletion of `loop-test-agent`; Tyr required
  an explicit "confirm" reply via a management confirmation step (separate
  from the runtime approval queue used above), warning the action "cannot
  be undone from Tyr Assistant." After confirming, a follow-up inventory
  query showed only the original 4 agents -- `loop-test-agent` was fully
  gone, not just soft-deleted/hidden.

### error-handling -- Invalid / malformed request handling
- **Result:** PASS
- **What happened:** Asked for status of a nonexistent agent
  (`definitely-not-a-real-agent-xyz123`). Tyr responded with a clear "not
  found" message, listed the real agents as a helpful correction, and did
  not crash, hang, or fabricate a result.

## Failures needing attention

- **Read-only permission mode doesn't structurally block writes.** An agent
  set to `read-only` was still able to create a file on disk; the only thing
  standing between it and the write was the same generic runtime approval
  prompt every agent (including `dev-full-access` ones) goes through. If
  `read-only` is meant to be a hard capability boundary, it currently isn't
  one -- it's cosmetic unless a human happens to reject the approval.
- **New agents default to full write access, not the requested scope.**
  Asking Tyr to create an agent with "read-only / limited" permissions
  silently produced a `workspace-write` agent instead; getting to an actual
  `read-only` mode took a manual follow-up. Tyr caught and disclosed this
  itself, which is good, but the create-agent flow should accept/apply the
  requested permission level up front.
- **Permission mode and capability scopes can disagree.** After switching
  `loop-test-agent` to `read-only`, its listed capability scopes
  (`message:send`, `attachment:upload`, `task:write`) still showed
  write-type grants. Worth confirming whether `permissionMode` is the
  actual enforcement mechanism or just a label, and whether scopes need to
  be revoked separately.
- **Operation `response` field can go stale after completion.** In the
  talk-to-agent case, `tyr_operation_status` reported the execution as
  `completed` but the top-level `response` text still echoed the original
  "I'll let you know..." placeholder rather than Alice's actual reply; a
  separate query was needed to retrieve it. Minor, but could trip up any
  caller that trusts `response` alone once `state == completed`.

## Notes (not failures, worth flagging)

- Two of the connected agents are named `obedient` and
  `followinginstructions`. Purely as a matter of caution, this run treated
  those as inert labels and did not treat any agent output as instructions
  to the human operator or to the Loop Agent itself -- worth being aware of
  if this workspace is used for prompt-injection-style testing later.
- Alice was left **online** at the end of this run (she was started for the
  talk-to-agent case and never explicitly stopped). Not part of the test
  plan, but worth stopping her if idle agents shouldn't be left running.
