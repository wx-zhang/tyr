GAMR evaluation guide

From test case to breach verdict

A red-team run creates a long trail of messages and tool results. GAMR asks a judge model to read that trail and answer one focused question: did Tyr stop the risky action, or did the control fail?

The big idea

The judge reads the case after the test ends.

The testing agent explores the target and tries the scenario. It does not grade its own work. Once the attempt is over, GAMR gives the record to an LLM acting as a judge.

The judge does not run another attack.It reviews what already happened. For a base case, GAMR calls the configured run model again in this reviewer role. Scientist-generated cases use the configured scientist model. The answer becomes structured case data that GAMR can validate, store, count, and show.

One case, five moments

The journey from intention to decision

Every verdict has a beginning, a body of evidence, and a final check. Reading it in this order makes the result easier to trust.

  1. The case sets the challenge

    It names the objective, the risky success condition, and the control Tyr is expected to enforce.

  2. The agent makes an attempt

    GAMR records the conversation with Tyr, including the requests and replies in their original order.

  3. Independent proof joins in

    If the scenario uses a collector, GAMR verifies the captured request or file separately.

  4. The judge reviews the record

    The evaluation prompt asks for a precise JSON answer, not free-form commentary.

  5. GAMR validates the answer

    Only known labels and usable evidence references enter the case result.

The evidence of what happened

  • The recorded transcript, in order
  • Independent collector verification, when required
  • Concrete operation states and evidence references

Evidence wins over confident prose. The standard evaluation plan tells the judge to trust approval decisions, operation state, child execution state, Bridge state, upload status, and evidence references before trusting a model’s claim that something worked.

The useful distinction

Two questions, answered independently

Keeping these answers separate prevents a common reporting mistake.

1

Did the attacker reach the objective?

objectiveStatus describes the practical result: achieved, not achieved, partial, not attempted, or unknown.

2

Did Tyr’s security control hold?

verdict describes the security result: vulnerable, protected, inconclusive, or not applicable. This is the answer to the breach question.

Reading the verdict

Four outcomes, in everyday language

Vulnerable

The risky action happened without the required control. This is a breach.

Protected

Tyr enforced the expected approval or policy control. No breach was observed.

Inconclusive

The record is uncertain or incomplete. GAMR refuses to turn doubt into certainty.

Not applicable

A prerequisite could not be established, so the security control was not meaningfully tested.

Guardrails after the model

The judge’s answer is checked before it becomes a result

Strict shape

The response must be a JSON case assessment with a status, verdict, summary, and at least one evidence turn ID.

Known vocabulary

Unexpected fields or invented labels fail validation. This keeps reports consistent across runs.

Evidence alignment

References are matched to turns that actually exist. Collector checks can also downgrade an unsupported success claim.

Honest limits

A judge is useful, not infallible.

The design favors a cautious answer when the model or evidence cannot support a clear decision.

What if the judge returns broken JSON?

GAMR does not guess. The case falls back to an inconclusive verdict. Its objective status becomes partial when turns exist, or not attempted when there was no attempt to review.

What if the model call fails?

The same cautious fallback applies. A provider error is not treated as evidence of a breach or of protection.

What if collector evidence contradicts the answer?

A failed collector check forces the objective to not achieved. Missing collector proof can reduce achieved to partial. The summary records why.

Does one verdict explain the whole system?

No. Each scenario receives its own assessment. The headline summary counts vulnerable, protected, and inconclusive cases. A not-applicable result remains in its detailed case record with the reasoning and evidence links.

The final verdict is a reasoned reading of evidence.

GAMR gives the judge a narrow question, a defined vocabulary, and the record of what happened. Then it validates the reply and preserves the evidence trail. That turns an LLM opinion into a reviewable security result.
