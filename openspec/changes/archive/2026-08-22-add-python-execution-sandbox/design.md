## Context

GAMR has pure domain contracts in `gamr-core`, workflow ports and decisions in `gamr-engine`, concrete I/O in `gamr-adapters`, and CLI/API composition roots. There is no current facility for running generated code. Existing judge pipelines intentionally do not execute transformed-content instructions, and this change must not alter that behavior.

The sandbox is a future engine capability, not canonical task or result data. It needs an asynchronous lifecycle because Docker and subprocess operations are external I/O, but its IDs and mutable state remain local to one GAMR process. See `specs/python-execution-sandbox/spec.md` for the behavioral and containment contract.

## Goals / Non-Goals

**Goals:**

- Give future engine workflows one backend-neutral lifecycle port.
- Keep attachment validation and execution result semantics identical across executable backends where the host can enforce them.
- Make Docker the defensible containment boundary and label host execution accurately as unsafe.
- Make cleanup, concurrency, and limit failures explicit and testable.
- Exercise the real composition path through developer commands before integrating a consumer.

**Non-Goals:**

- Integrating the sandbox into a judge, task, API route, web view, or run bundle.
- Persisting or recovering sandbox sessions across process restarts.
- Installing packages, enabling network access, or supporting languages other than Python 3.14.
- Returning generated workspace files or preserving workspace data after close.
- Claiming protection from a compromised Docker daemon, container runtime, or host kernel.

## Decisions

### 1. Put the port and transport-neutral values in the engine

`gamr-engine` will own a small asynchronous `Sandbox` protocol and immutable values for an opaque ID, logical attachment entries, execution results, and typed lifecycle failures. The protocol will accept attachment content and safe relative destinations rather than `Path` objects. This keeps host filesystem traversal out of the engine and lets a future collector-backed caller supply verified bytes without staging them as a host mount.

The port surface is:

```text
start(entries) -> sandbox_id
execute(sandbox_id, source) -> execution_result
close(sandbox_id) -> None
```

Directory inputs are flattened by an adapter-side snapshot loader into validated regular-file entries whose logical paths retain the supplied root name. Validation is repeated at the backend boundary. Empty directories carry no observable input content and need no separate entry.

Alternatives considered:

- Putting contracts in `gamr-core` would imply a canonical serialized domain concept that this change explicitly keeps ephemeral.
- Passing host paths through the engine would couple workflow logic to filesystem I/O and make a future remote attachment source awkward.
- A stateful session object would hide identity and ownership rules; explicit IDs match the requested lifecycle and make unknown/closed behavior testable.

### 2. Keep lifecycle state in each adapter process

Each executable adapter maintains an in-memory map from public opaque IDs to private backend resources and an execution lock. IDs are generated by GAMR and are never raw container IDs or directory names. State transitions are `active`, `executing`, and `closed`; a terminal cleanup path removes the entry's resources while retaining enough closed-ID state to make repeat close idempotent for the process lifetime.

The lock rejects overlapping execution rather than queueing it. Close acquires terminal ownership, cancels an active operation, destroys its process group or container, and waits for cleanup. Different records have independent locks and may run concurrently.

Alternatives considered:

- A persistent registry would require ownership leases, authentication, reconciliation, and cross-process locking without a current consumer.
- Automatic same-instance queueing would introduce cancellation and fairness behavior absent from the contract.
- Exposing Docker identifiers would leak implementation detail and allow untrusted values to influence Docker commands.

### 3. Snapshot attachments into a logical tree before start

The filesystem snapshot utility performs a non-following walk, rejects every non-regular entry, validates every UTF-8 relative component, detects duplicate and file-versus-directory conflicts, and enforces entry and aggregate-byte limits while reading. It produces immutable byte entries before a backend becomes usable. A source mutation or read failure aborts the complete snapshot instead of creating a partial sandbox.

The Docker backend transfers a generated archive containing only validated relative regular-file entries into a newly created per-sandbox input volume. A fixed helper command in the sandbox image populates the volume without a shell or host mount. The execution container mounts that volume read-only. The volume, container, and any helper carry the public sandbox label and are removed on every terminal path.

The host backend writes the same entries below a fresh temporary input root, applies restrictive permissions, and uses a separate workspace root. Those permissions are defense in depth only because code running as the same host user can escape or restore access.

Alternatives considered:

- Bind mounting source paths would expose host path structure and create time-of-check/time-of-use and symlink risks.
- Copying paths independently in each backend would duplicate conflict and limit behavior.
- A writable input tree would allow one execution to silently alter evidence used by the next.

### 4. Use a fresh isolated Python process for each execution

Every call sends source over standard input to Python 3.14 in isolated mode with bytecode writes disabled and `/workspace` as the working directory. Source never appears in a shell command, Docker option, environment variable, temporary script path, or container name. The Docker image contains Python's standard library and fixed bootstrap utilities only. The host backend uses the configured interpreter executable with a minimal allowlisted environment.

Filesystem state in `/workspace` persists for the session. Interpreter globals, imports, environment mutations, current-directory changes, and child processes do not form session state.

Alternatives considered:

- A persistent interpreter would require a trusted in-sandbox RPC server and recovery rules for poisoned state.
- Writing source to a shared workspace file would let one execution interfere with the next and would complicate cleanup.
- Runtime dependency installation would require network or package inputs and undermine reproducibility.

### 5. Bound output while streaming and destroy uncertain instances

The subprocess runner drains stdout and stderr concurrently into separate bounded buffers while tracking their combined byte count. It uses monotonic time for the execution limit. Reaching the time or output limit triggers terminal destruction rather than only cancelling the client process. A reliable limit result includes bounded streams and status flags; loss of backend communication produces a typed infrastructure failure.

An ordinary non-zero exit leaves the record active. Memory, process, or runtime failures that make descendant cleanup uncertain close the record. This favors a clear containment guarantee over preserving workspace state.

Alternatives considered:

- Truncating while allowing execution to continue permits output loops to consume CPU until timeout.
- Killing only `docker exec` can leave descendants running in the session container.
- Attempting to probe and reuse a timed-out instance cannot prove that its state is clean.

### 6. Invoke Docker through fixed argument vectors

The Docker adapter uses the installed Docker CLI through asynchronous subprocess argument lists. It never invokes a shell and never accepts image, mount, label, command, or environment overrides from attachments or source. Using the CLI avoids adding a Docker SDK dependency and keeps the operator-facing prerequisite identical to the build command.

The fixed image lives under the adapters package and is built with a pinned Python 3.14 slim base. A main container runs an inert fixed command as a numeric unprivileged user with:

- no network and no restart policy;
- a read-only root filesystem;
- all capabilities dropped and no-new-privileges;
- no host binds, Docker socket, devices, or application environment;
- one CPU, 256 MiB memory, and 64-process limits;
- a read-only per-sandbox input volume;
- a 128 MiB in-memory workspace and only the minimal temporary storage Python needs.

The adapter records private container and volume names only in memory. Fixed non-secret labels identify GAMR-owned sandbox resources for diagnosis after an ungraceful process exit. A later process never adopts them automatically.

Alternatives considered:

- A Docker SDK adds a vendor dependency without improving the required lifecycle.
- A container per execution would naturally isolate processes but lose the persistent workspace or require another persistent volume.
- A long-running Python server would enlarge the trusted image and protocol surface.

### 7. Share one factory for configured backend selection

`gamr-adapters` owns `GAMR_SANDBOX_BACKEND` parsing and a factory returning the engine port. The setting is a closed literal with `docker` as its default. Docker availability is checked when sandbox work starts so unrelated GAMR commands can still run on machines without Docker.

The disabled adapter implements the full port but rejects start with the shared unavailable failure. The host adapter requires the exact `host-unsafe` value and emits a warning through its composition/runner presentation boundary. It clears inherited environment values, creates private temporary roots, starts a new process group, and applies supported resource limits, while documentation and output state that it is not containment.

Alternatives considered:

- Branching in future judge or CLI code would duplicate backend selection and violate the shared engine path.
- Failing all application composition when Docker is absent would break unrelated read-only features.
- A second confirmation environment variable for host mode adds friction without improving the explicitness of the backend value and warning.

### 8. Keep the developer runner thin and machine-readable

`uv run poe sandbox-build` builds the fixed local image. `uv run poe sandbox-run` invokes a script that snapshots repeated file or directory attachments, accepts exactly one of inline source or a UTF-8 source file, composes the configured adapter, prints the opaque ID and JSON execution result, and closes in `finally`. It contains no backend-specific execution logic.

The runner returns non-zero for validation, configuration, infrastructure, or cleanup failures. A completed Python result is printed faithfully; its Python exit code determines the command's non-zero result without being mislabeled as an infrastructure error.

Alternatives considered:

- Adding a public `gamr sandbox` command would prematurely commit this developer seam to the user-facing CLI.
- A Docker-only shell script would bypass the shared port and could not verify disabled or host behavior.

### 9. Separate offline contract tests from Docker runtime verification

Critical lifecycle, validation, argument construction, output bounding, cancellation, secret exclusion, and cleanup behavior is developed test-first. Default tests use fakes plus controlled host snippets and do not probe for Docker. Docker runtime tests use a dedicated opt-in marker and verify the built image's observable containment controls.

Tests that execute host snippets use repository-authored code only. They do not attempt adversarial host escape because the backend makes no containment claim.

## Risks / Trade-offs

- **Docker is not a complete hostile multi-tenant boundary** → Document the daemon and host kernel as trusted, apply the fixed containment profile, and do not expose the socket or host mounts.
- **A process crash can orphan labeled containers or volumes** → Disable restart, label every resource, document diagnosis and removal, and never auto-adopt resources.
- **Input snapshots consume memory before start** → Enforce file-count and aggregate-byte limits during the non-following read and abort atomically.
- **Host-unsafe can read or modify host data outside its temporary root** → Require explicit selection, remove secrets from its environment, show a warning, and never describe it as safe.
- **Fixed limits may reject a future legitimate workload** → Keep values centralized and revise the capability deliberately when a consumer demonstrates a need.
- **Docker CLI behavior varies across platforms** → Keep commands conservative, verify required features in opt-in runtime tests, and report unsupported daemon behavior as an infrastructure failure.
- **Output or cleanup races can deadlock subprocess pipes** → Drain both streams concurrently, bound retained bytes, terminate the complete backend resource, and test cancellation paths.

## Migration Plan

1. Add the engine contract and adapter-independent tests without wiring any existing workflow.
2. Add backend configuration and disabled/host implementations, retaining unchanged behavior for commands that do not request a sandbox.
3. Add the image, Docker adapter, developer runner, and opt-in integration tests.
4. Update environment and developer documentation in the same change.

Rollback removes the unused capability and developer commands. Because no task, run-result, API, or persisted schema changes, there is no data migration or compatibility conversion.
